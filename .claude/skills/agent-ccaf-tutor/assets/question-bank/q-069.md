## Question

In a CI pipeline, Claude Code generates a feature implementation across nine files, then — in the same session — is asked to review its own output before the PR opens.

The review is consistently weak. It confirms the design decisions it just made and misses two classes of bug that a human reviewer catches within minutes: an off-by-one in a loop it wrote, and an unhandled null in a helper it created.

What change most improves review quality?

## Options

- **A)** Enable extended thinking for the review step so the model reasons more deeply before reporting findings.
  - **Rationale:** More thinking on top of the same biased premises. The problem is not too little reasoning effort — it is that the reasoning starts from the model's own generation context, where the design decisions already look settled. Extended thinking makes the existing conclusions better argued, not more questioned.
- **B)** Run the review in a separate, independent Claude instance that receives only the diff and the review criteria, with no access to the generation session's reasoning.
  - **Rationale:** Correct. The exam guide (T4.6) states it directly: a model retains reasoning context from generation and is therefore less likely to question its own decisions in the same session. An independent instance has no stake in the design and no memory of why a choice was made — it sees the code as an artifact to be judged. This is the same principle as the T3.6 CI guidance to review in a fresh session rather than with `--resume`.
- **C)** Strengthen the review prompt: instruct it to be adversarial, assume the code is wrong, and check every loop boundary and null path explicitly.
  - **Rationale:** Better criteria genuinely help reviews in general (T4.1), which is what makes this tempting. But it cannot remove the structural bias: the same session still carries the reasoning that produced the code, so "assume it is wrong" competes with a context that already explains why each choice was right. Prompt wording is a probabilistic fix for what is a context-isolation problem.
- **D)** Have the generating session self-report a confidence score per file, and route the low-confidence files to a human reviewer.
  - **Rationale:** Builds on an unreliable signal. Self-reported confidence from the session that wrote the code inherits the same bias — it is confident about the off-by-one precisely because it believes the loop is right. Confidence self-reporting can supplement a verification pass, but it cannot replace independent review, and it quietly hands the missed-bug problem to humans instead of fixing it.
