## Question

A team keeps a skill at `.claude/skills/migration-dry-run/SKILL.md`. It replays the pending database migration against last night's snapshot. A full run takes about 25 minutes, and it finishes by printing a six-line summary: tables touched, rows affected, estimated downtime, and any blocking errors.

A teammate opens a PR adding `context: fork` to its frontmatter. Their PR description says: "This is by far the longest-running skill we have — it shouldn't be hogging the main conversation."

What is the right call on that PR?

## Options

- **A)** Reject it. The skill returns six lines, so it costs the main context almost nothing — forking would add indirection without solving any real problem.
  - **Rationale:** Correct. The test for `context: fork` is one question: would this skill's output flood the main conversation? Six lines does not. Forking here buys nothing and costs clarity — the skill would run in a separate subagent that cannot see the conversation history, and the summary would arrive second-hand for no reason. Not reasons to fork: how long it runs, whether it touches the filesystem, or wanting to do something else meanwhile.
- **B)** Approve it. A 25-minute skill is exactly the kind of thing `context: fork` exists for.
  - **Rationale:** The duration trap. `context: fork` isolates *context* — the tokens a skill's output would otherwise put into the main conversation. Wall-clock runtime is not a context cost. A 25-minute skill that prints six lines leaves the main thread almost exactly as it found it.
- **C)** Approve it, but for a different reason — forking keeps the dry run from being able to touch the live database.
  - **Rationale:** Conflates two frontmatter fields. Restricting which tools a skill can use is `allowed-tools` (in exam-guide terms; current Claude Code uses `disallowed-tools` for that). A forked skill runs in an isolated *context*, not a sandbox — it has the same tool access it always had.
- **D)** Approve it, because forking lets the migration simulation run in the background while the developer keeps working in the main conversation.
  - **Rationale:** Forking is not concurrency. `context: fork` is about where the skill's output lands, not about running things in parallel. This reasoning would lead to forking every slow skill and none of the noisy ones.
