## Question

A repo runs an automated job every time someone pushes to a pull request. The job checks out the branch, runs Claude Code non-interactively over the diff with a review prompt, gets structured findings back, and posts each finding as an inline comment on the PR. It works.

The problem is re-runs. A developer pushes three more commits to fix the review comments. The job runs again from scratch, re-reviews the whole diff, and re-posts all 40 of its original comments — including the ones already fixed. Developers have started ignoring the bot.

What is the right fix?

## Options

- **A)** Have the job review only the diff of the newest commit rather than the whole branch diff.
  - **Rationale:** Cheap, and it does cut the duplicates, but it blinds the review. A fix in commit four can break something introduced in commit one, and reviewing only the newest slice means no pass ever sees the branch as a whole. It also permanently hides any issue in earlier commits that the first run happened to miss. Narrowing the input is not the same as knowing what was already said.
- **B)** Pass the previous run's findings into the job as context and instruct Claude to report only issues that are new or still unaddressed.
  - **Rationale:** Correct. This is the exam guide's (T3.6) advice for re-runs on new commits: include the prior findings and ask for only new or still-unaddressed issues. It keeps the full-branch diff in view and lets the model *check whether each earlier finding was actually resolved* by the new commits, rather than guessing from the fact that a line changed. Fixed issues drop off, unfixed ones stay, genuinely new ones appear.
- **C)** Post-process the findings in the pipeline: string-match each new comment against the comments already on the PR and suppress exact duplicates.
  - **Rationale:** Deduplication mistaken for resolution tracking. It is brittle — a reworded description or a line number shifted by an edit above it defeats the match — and it gets the meaning backwards: a finding that is still valid *should* be repeated, and one that was fixed should disappear. String matching cannot tell those apart because it never checks whether the code changed.
- **D)** Raise the severity threshold on re-runs so only high-severity findings are re-posted.
  - **Rationale:** Cuts the volume by throwing away real signal. Medium-severity findings do not stop mattering because the job ran twice, and a developer who fixed a high-severity issue still sees it re-posted. It treats comment count as the problem when the real problem is that the job has no memory of what it already reported.
