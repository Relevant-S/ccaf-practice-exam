## Question

A customer-support agent handles incoming chat sessions. The team needs to decide when the agent should pause and ask the customer a clarifying question vs proceed with its best interpretation of an ambiguous request.

Which approach will most reliably catch the cases that genuinely need clarification?

## Options

- **A)** Instruct the agent in the system prompt: ask a clarifying question when (a) the request is materially ambiguous and a wrong interpretation would lead to a costly or irreversible mistake, (b) multiple plausible interpretations would lead to materially different actions, or (c) the customer's stated outcome is at odds with what they're literally asking for. Otherwise proceed with the best interpretation and verify before any irreversible action.
  - **Rationale:** Correct. Clear, explicit criteria handed to the model. The conditions — "materially ambiguous," "costly mistake," "outcome at odds with request" — are the contextual judgments LLMs are good at and rules systems are bad at. The criteria generalize to ambiguity shapes the team hasn't seen yet.
- **B)** Build a decision tree mapping request categories to clarification rules: "if request type = refund AND amount is unspecified → ask"; "if request type = order status AND multiple matches → ask"; etc. Maintain the tree as new ambiguity patterns are discovered.
  - **Rationale:** Decision trees of pre-set categories break on the long tail of real customer requests. They handle the patterns the team anticipated and fall back to "proceed anyway" for everything else — which is most of the actual ambiguity.
- **C)** Have the agent self-report a 0–100 confidence score on its interpretation of each incoming request. Ask a clarifying question whenever confidence is below 75.
  - **Rationale:** Self-reported confidence is an unreliable proxy for case complexity — models can be confidently wrong, especially on edge cases that look familiar on the surface. The exam guide (T5.2) names this as an anti-pattern; a clean threshold *looks* engineered but doesn't measure what matters.
- **D)** Pattern-match incoming requests against a curated library of known-ambiguous request templates maintained by the support team. Ask for clarification only when the request matches a template.
  - **Rationale:** A template library only catches ambiguity shapes the team thought to list. Every new kind of ambiguity falls through without clarification. The maintenance burden is also continuous — the library is always out of date.
