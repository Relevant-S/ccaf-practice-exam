## Question

Your extraction system processes two document types: standard monthly reports (archived after processing) and urgent exception reports (must trigger business alerts within 30 minutes of receipt). Both use the same JSON schema. You want to minimize API costs while meeting latency requirements.
How should you architect the processing pipeline?

## Options

- **A)** Route standard reports to the `Batch API` for 50% cost savings, and route urgent exception reports to the real-time Messages API.
  - **Rationale:** Correct. Match latency profile to document urgency: batch for the bulk (cheap), real-time for the latency-sensitive exceptions (fast). Minimizes cost while meeting SLA.
- **B)** Submit all documents to the real-time Messages API to ensure consistent processing latency across document types.
  - **Rationale:** Consistent but expensive. Standard monthly reports don't need real-time latency and shouldn't pay for it.
- **C)** Queue all documents and submit hourly batches, flagging urgent documents for expedited handling when batch results return.
  - **Rationale:** Hourly batches still ride the batch SLO and don't guarantee the 30-minute alert window for exceptions.
- **D)** Submit all documents to the `Batch API` with `custom_ids` for tracking. When results arrive, immediately process urgent documents and trigger delayed alerts for exceptions.
  - **Rationale:** Batch has up to a 24-hour window — 30-minute alerting SLAs on exception reports can't be met by routing them through batch.
