## Question

A deprecated helper called `formatLegacyAmount` needs removing.

A search has already been run: it is referenced in exactly three files, and each reference is a single call site.

The agent needs to understand what each call expects so it can replace it correctly. The repository is large — around 12,000 files across nine packages — and nobody on the team has a complete picture of it.

How should the agent proceed?

## Options

- **A)** Read the three files directly and work out what each call site needs.
  - **Rationale:** Correct. The search has already shrunk the problem to three files and three call sites — small enough to read in full. Any further machinery (indexes, subagents, exploration strategies) is scaffolding for a search that has already succeeded.
- **B)** Spawn parallel subagents to explore the packages, since no single person understands a 12,000-file repository.
  - **Rationale:** Repository size governs how hard it is to *find* something, and it has already been found. Fanning out here pays the cost of parallel investigation to rediscover three files the agent could open now — premature fan-out.
- **C)** Build a searchable index of the repository first, so this removal and future ones are cheaper.
  - **Rationale:** Infrastructure ahead of need. It might pay off across many future tasks, but it is a large detour in front of a three-file change, and nothing in the scenario suggests a programme of similar removals.
- **D)** Have the agent summarise each of the nine packages first, to establish context before touching the call sites.
  - **Rationale:** Context-gathering the task does not require. The agent needs to know what three specific call sites expect, and that is visible in three files. Nine package summaries cost real context and answer a question nobody asked.
