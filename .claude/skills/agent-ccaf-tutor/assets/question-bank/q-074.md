## Question

A bug report: the signup form accepts a date of birth in the future, so a handful of accounts have birth years like 2087.

Looking at the code: there is one validator function, `validateSignup`, in one file. It checks the email and the password but never checks the date. The fix is a single conditional rejecting dates after today. There is an existing test file for this validator with the same shape of assertion already in it.

How should the developer direct Claude Code?

## Options

- **A)** Use plan mode, because the change touches validation logic and a mistake would let bad data into production.
  - **Rationale:** Cost of a mistake is the wrong trigger. Plan mode exists to resolve *design uncertainty* — several viable approaches, architectural consequences, changes spanning many files. It does not make a change safer to execute; tests and review do that. Reaching for plan mode whenever a change feels important means planning everything.
- **B)** Use plan mode with the Explore subagent first, to map every call site of `validateSignup` before deciding on the fix.
  - **Rationale:** Two mechanisms used for a problem that has neither symptom. The Explore subagent earns its cost when discovery is verbose and would flood the main context; here the relevant code is one function in one known file, already read. Call sites do not matter because the function's signature and contract are unchanged — the fix adds a check inside it, not a change to how it is called.
- **C)** Use plan mode as a standing policy for anything that ships to production, so there is always a reviewable plan before code changes.
  - **Rationale:** A process rule standing in for a judgment. Blanket plan mode adds a round trip to every trivial fix, and plans for one-line changes are noise that trains the team to skim them — which is worse than having none when a change genuinely needs one. Reviewability comes from the diff and the tests, not from a pre-written plan.
- **D)** Direct execution: add the conditional and extend the existing test file.
  - **Rationale:** Correct. This is the textbook direct-execution case — a single-file change, one obvious implementation, scope fully understood before starting, and an existing test pattern to follow. There is no design decision to surface, so a planning round would produce a plan with exactly one step. The exam guide (T3.4) names this exact shape (adding a date validation conditional) as its direct-execution example.
