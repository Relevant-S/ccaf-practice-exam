## Question

In a multi-agent research system, a coordinator delegates to a web-search subagent, a document-analysis subagent and a synthesis subagent.

On one run the web-search subagent issues seven queries. Five return results. Two fail — the search API times out on both, and retrying them once does not help.

How should the web-search subagent report back to the coordinator?

## Options

- **A)** Return the five successful result sets and treat the run as successful, since partial results are still usable and the coordinator does not need to know about transient infrastructure noise.
  - **Rationale:** Silent suppression, which the exam guide (T5.3) names as an anti-pattern. The coordinator now believes it has full coverage of all seven queries, and the synthesis agent will write with unearned confidence about topics that were never searched. A gap nobody knows about is worse than a gap that is reported.
- **B)** Return the five successful result sets plus structured error context for the two failures: the failure type, the queries that were attempted, and what alternatives might work — so the coordinator can decide whether to re-delegate, try another source, or proceed with an annotated gap.
  - **Rationale:** Correct. This is the full T5.3 pattern: the subagent recovers locally where it can (it already retried), then passes up only what it could not resolve, with partial results and a record of what was attempted. Structured context is what lets the coordinator recover intelligently rather than guess — and it lets the synthesis output carry coverage annotations marking which findings are well supported and which topic areas have gaps.
- **C)** Fail the whole run and return an error to the coordinator, so no synthesis is produced from incomplete data.
  - **Rationale:** The other anti-pattern T5.3 names: ending an entire workflow on a single failure. Five of seven queries succeeded and the document-analysis subagent's work is untouched — throwing all of it away for two timeouts is out of proportion. Whether partial coverage is good enough is the coordinator's call, not the subagent's.
- **D)** Return the five result sets with a status field reading "search partially unavailable," keeping the message short so it does not consume coordinator context.
  - **Rationale:** It does flag the problem rather than hiding it. But a generic status hides the context that drives recovery: which queries failed, whether it was a timeout or a permission error, whether a retry or another source is worth trying. The coordinator can tell something went wrong but not what to do about it, so it cannot re-delegate the two specific queries or annotate which topics are thin.
