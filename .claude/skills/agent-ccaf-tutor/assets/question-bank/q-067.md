## Question

A compliance team must extract the same 12 specific data points (effective date, jurisdiction, liability cap, termination clause, etc.) from each of 340 vendor contracts. The 340 contracts are already identified and sitting in a folder. The 12 fields are fixed and known up front. Each contract is independent — extracting from contract #5 tells you nothing about contract #200. The job must finish tonight.

How should this workload be decomposed?

## Options

- **A)** Fan out: run the same fixed 12-field extraction over all 340 contracts in parallel (batched concurrent subagents / a parallel pipeline), each contract processed independently with the identical structured-extraction prompt.
  - **Rationale:** Correct. The work set is known, complete and independent, and the decomposition (12 fixed fields per contract) is fully determined before any work starts. There's no runtime lead to follow and nothing to adapt, so a fixed parallel fan-out is exactly right. It minimizes wall-clock time and gives consistent output. Adaptive judgment would add latency and variance for zero benefit — the exam guide (T1.6) reserves dynamic decomposition for open-ended investigation.
- **B)** Have a coordinator read each contract first, decide adaptively which of the 12 fields are relevant to that contract, and extract only those — pursuing leads as they emerge.
  - **Rationale:** Over-applies the adaptive pattern. The 12 fields are fixed and required for all 340 — there's no judgment to make about which fields matter, and "pursuing leads" invents runtime decisions the task doesn't have. This adds latency and inconsistency (different contracts getting different field sets) to a fully specified problem. Adaptive decomposition is for when the path is unknown; here it's known.
- **C)** Process the 340 contracts sequentially in a single long-running agent session, accumulating all extractions in one growing context so the agent can cross-reference contracts as it goes.
  - **Rationale:** Two problems. The contracts are independent, so cross-referencing buys nothing — and accumulating 340 contracts in one context invites lost-in-the-middle degradation and blows the deadline by serializing work that could run in parallel. Sequential-with-shared-context is the wrong tool when items are independent and the clock matters.
- **D)** Build a classifier that routes each contract to one of several contract-type-specific extractors, then run those.
  - **Rationale:** Unnecessary structure. The same 12 fields are extracted from every contract regardless of type, so a routing layer adds a new way to fail (misroutes) and complexity for no gain. Classification helps when downstream handling genuinely differs; here it doesn't.
