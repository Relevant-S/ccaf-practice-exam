## Question

Claude Code has generated a caching layer. Reviewing it, the developer finds three problems:

1. Entries are written with no TTL, so nothing ever expires on its own.
2. The invalidation hook fires on write but not on delete, so deleted records stay readable from cache.
3. Reads that miss the cache repopulate it *before* the surrounding transaction commits, so a rolled-back transaction leaves a phantom entry behind.

The third problem's correct fix depends on what is decided about the first two — a short enough TTL changes how much the phantom entry matters, and moving repopulation after commit interacts with when invalidation should fire.

How should the developer feed this back?

## Options

- **A)** Report them one at a time, starting with the TTL, verifying each fix before raising the next.
  - **Rationale:** The right technique for the wrong kind of problem. Sequential iteration suits *independent* issues, where fixing one cannot change the right fix for another and one-at-a-time keeps each change reviewable. Here the three are explicitly linked, so fixing the TTL alone means the invalidation and commit-ordering decisions get made without it in view — and each later round may have to revisit the earlier fix.
- **B)** Report the phantom-entry bug alone, since it is the most severe, and open tickets for the other two.
  - **Rationale:** Separates the one problem that cannot be solved alone from its own context. The commit-ordering fix depends on the TTL and invalidation decisions, so solving it first means guessing at them — and the guesses get built into the fix. Severity is a good guide to ordering when issues are separable; these are not.
- **C)** Report all three and ask Claude to redesign the caching layer from scratch with correct expiry, invalidation and transaction semantics.
  - **Rationale:** Throws away working code to avoid three connected fixes. Most of the layer is presumably fine, and a from-scratch rewrite swaps three known, well-understood bugs for an unknown set in new, unreviewed code. Redesign is warranted when the structure itself cannot take the fix; nothing here says that.
- **D)** Send all three in a single detailed message, describing how they interact, and let Claude resolve them together.
  - **Rationale:** Correct. The exam guide (T3.5) draws the line exactly here: multiple *interacting* problems go in one detailed message; independent ones go sequentially. Because the fixes constrain each other, only a single pass that sees all three can pick a coherent set — a TTL, an invalidation trigger and a repopulation point that agree with one another. Stating the interaction explicitly is the key part; it stops each fix being optimised on its own.
