## Question

Your team of three developers is standardizing on Claude Code with an MCP server that talks to your company's internal Jira instance. Requirements:

- All three developers should use the same MCP server implementation and the same Jira URL (no drift across machines).
- Each developer authenticates to Jira with their own personal API token (not a shared service account — Jira audit logs must show the real human).
- Tokens must not be committed to version control.

How should you configure this?

## Options

- **A)** Put the server in `.mcp.json` at the project root and commit the developers' literal tokens into the file — one per developer, distinguished by username.
  - **Rationale:** Committing personal API tokens to version control is a credential leak. Anyone with repo access (including future hires, vendors, or attackers if the repo leaks) gets working credentials for every developer.
- **B)** Put the server in `.mcp.json` at the project root with environment-variable expansion (e.g., `${JIRA_TOKEN}`) for the credential field. Each developer sets `JIRA_TOKEN` in their own shell environment.
  - **Rationale:** Correct. Project scope (`.mcp.json`) is the right place for shared server config — URL and implementation are identical across the team and tracked in version control. Environment-variable expansion (`${JIRA_TOKEN}`) keeps secrets out of the committed file while giving each developer their own credential. This is the T2.4 pattern for sharing MCP server config without leaking secrets.
- **C)** Each developer adds the server independently to their personal `~/.claude.json` (user scope), pasting their own token literal into that file.
  - **Rationale:** User scope is for personal or experimental servers — it does not solve the "everyone uses the same implementation" requirement. Drift is guaranteed over time: someone upgrades the server URL, someone else doesn't, and the team starts debugging "works on my machine" issues.
- **D)** Put the server in `.mcp.json` at the project root, pointing at a single shared service-account token committed alongside it.
  - **Rationale:** A shared service-account token defeats the audit requirement — Jira logs cannot attribute actions to the real human. It is also a committed secret, and rotating it requires coordinating all three developers at once.
