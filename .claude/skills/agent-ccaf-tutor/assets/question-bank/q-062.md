## Question

A developer brings four tasks to Claude Code in succession. Which one is the strongest case for plan mode rather than direct execution?

## Options

- **A)** "The deploy script is missing a `--region us-east-1` flag on the `aws s3 sync` call in `scripts/deploy.sh`. Add it."
  - **Rationale:** One file, one line, a deterministic change with no design decision to surface. Direct execution is the right fit — plan mode would be process for its own sake.
- **B)** "Add a `validate_iso_date(s)` helper to `utils/dates.py` that returns True/False, and import it where `process_invoice` parses dates."
  - **Rationale:** Two files, but the design is fully specified — function name, signature and integration point are all named. No architectural ambiguity to resolve before writing code. Direct execution.
- **C)** "I need to enable Redis caching in the API layer. The team has used three patterns in other projects — cache-aside, write-through, write-behind — and I'm not sure which fits our read/write profile. Help me decide, then roll it out across the ~30 endpoints that need it."
  - **Rationale:** Correct. Several valid approaches (three caching patterns) must be chosen between *before* implementation begins, and the choice spreads across ~30 endpoints. That is the core plan-mode trigger in T3.4: architectural ambiguity that must be resolved up front, where committing to the wrong pattern early would cost significant rework. Plan mode allows read-only research and a plan comparing the three patterns against the actual read/write profile before any code is written.
- **D)** "Rename `getUserProfile()` to `fetchUserProfile()` across the codebase. There are ~60 callers."
  - **Rationale:** Large blast radius, but the change is mechanical and the design is unambiguous — it's a rename, not an architectural decision. Direct execution with a find-and-replace or refactoring pass is appropriate. The risk (missing a call site) is a coverage problem, not a planning problem.
