## Question

A developer is having Claude Code write a converter that turns legacy log lines into structured events. The developer described the target format in a careful paragraph: how to split the timestamp, what to do when the severity token is missing, how to handle a trailing key-value tail.

Three attempts, three different interpretations. Each run is internally consistent and each reads like a defensible reading of the paragraph — one treats a missing severity as `null`, another as `"INFO"`, another drops the line. The prose is not wrong; it is just being read differently each time.

What is the most effective next step?

## Options

- **A)** Give it two or three concrete before-and-after examples — actual log lines paired with the exact structured output wanted, including one line with a missing severity.
  - **Rationale:** Correct. The failure is about interpretation, not capability, and concrete input/output pairs remove the interpretation entirely — an example showing a missing-severity line mapped to `null` is unambiguous in a way no paragraph about missing severities can be. The exam guide (T3.5) puts this first: when prose is read inconsistently, 2–3 concrete examples beat more prose. It also pins down the edge cases, which is where the three runs actually diverged.
- **B)** Rewrite the paragraph more precisely and emphatically, spelling out each rule as a numbered requirement with the ambiguous cases called out.
  - **Rationale:** More of the thing that is already failing. Careful prose has now been misread three times, and numbering the sentences does not change the fact that natural language allows several consistent readings. It can help at the margin, but better wording does not fix a problem with the channel itself.
- **C)** Define a JSON schema for the event and have the converter validate every output against it.
  - **Rationale:** Schemas are the right answer to a neighbouring problem, which is why this is tempting. A schema constrains the *shape* of the output — field names, types, required keys — and all three attempts would very likely pass it, since the disagreement is about what value a missing severity should take, not the structure holding it. Schemas remove syntax and shape errors, not disagreements about meaning.
- **D)** Use the interview pattern: ask Claude to question the developer about the log format until the requirements are pinned down.
  - **Rationale:** A real technique aimed at the wrong gap. The interview pattern helps when the developer has not yet thought the problem through — unfamiliar domains, unconsidered failure modes. Here the developer knows exactly what they want for every case; the difficulty is getting it across. Interviewing produces answers the developer already holds, in the same prose that is being misread.
